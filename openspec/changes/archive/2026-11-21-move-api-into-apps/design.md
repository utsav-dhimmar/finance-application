# Design

## Context

`@finance-application/api` lives at `server/api/` and is the only workspace member outside the `apps/*` / `packages/*` globs. See proposal.md for motivation. Constraints that shape the approach:

- CI invokes `turbo run` from the repo root and contains no path references — the move must not require CI edits.
- The API worker serves the built web SPA via wrangler static assets (`assets.directory` → `../../apps/web/dist/client`), and its `turbo.json` declares `build` as dependent on `@finance-application/web#build`. Both must keep working at the new location.
- Production deploys run through Cloudflare Workers Builds, whose dashboard-configured build root directory points at `server/api` (per the `wrangler.jsonc` name comment). This lives outside the repo.
- All verified config paths inside the package are package-root-relative (`./src`, `./migrations`, `./tests/...`, `./wrangler.jsonc`) except two: `wrangler.jsonc`'s assets directory (cross-package, must change) and `tsconfig.json`'s `extends: ../../tsconfig.base.json` (depth-identical at `apps/api/`, unchanged).
- Tracked files in `server/api/` are exactly: `.dev.vars.example`, `command-list.md`, `drizzle.config.ts`, `migrations/**`, `package.json`, `scripts/**`, `src/**`, `tests/**`, `tsconfig.json`, `turbo.json`, `vitest.config.ts`, `vitest.workers.config.mts`, `worker-configuration.d.ts`, `wrangler.jsonc`. `dist/` is untracked build output.

## Goals / Non-Goals

**Goals:**

- Relocate the package intact so every file's content except `wrangler.jsonc` is byte-identical after the move.
- Preserve file history via rename detection.
- Leave repo, docs, and code comments pointing only at the new path.
- Land the repo change and the Cloudflare dashboard change in a verified order that keeps production deploys correct.

**Non-Goals:**

- No rename of the npm package (`@finance-application/api` stays).
- No restructure of the package internals (src layout, test layout, scripts stay as-is).
- No changes to CI workflows, turbo task graph semantics, build outputs, or deploy artifacts.
- No spec changes — every existing requirement is location-agnostic (declared `skip_specs: true`).

## Decisions

### D1: `git mv` the whole directory, not copy-and-delete

`git mv server/api apps/api` in one step, then patch `wrangler.jsonc`. Rationale: rename detection preserves per-file history (`git log --follow`), and one atomic move avoids a window where the package exists in neither location. Alternative considered — recreating files at the new path to "clean up" history: rejected, it destroys blame continuity for no benefit. Note `git mv` only moves tracked files; the untracked `dist/` is simply left behind and regenerated by the build.

### D2: Single content edit — the wrangler assets path

`assets.directory` becomes `../web/dist/client`. Every other config was verified to survive: package-root-relative paths (`drizzle.config.ts`, both vitest configs, `tsconfig.json` include globs) are depth-independent; `tsconfig.json`'s `../../tsconfig.base.json` resolves to the same root file because `apps/api/` is the same depth from the repo root as `server/api/`. The existing `build` script (`wrangler deploy --dry-run --outdir=dist`) validates the corrected path without a real deploy. Alternative considered — making the assets path configurable per environment: rejected, a static relative path matches the existing repo convention.

### D3: Workspace globs — drop `server/*`, rely on `apps/*`

`pnpm-workspace.yaml` keeps `apps/*` and `packages/*`; the `server/*` glob is removed and `server/` is deleted. `pnpm install` regenerates `pnpm-lock.yaml` (importer path metadata only). Alternative considered — keeping the `server/*` glob for future use: rejected, an empty glob is misleading; AGENTS.md says don't create directories before they're needed, and the same principle applies to globs.

### D4: Sequencing the Cloudflare dashboard change

Order: land the repo change on `main` → update the Workers Builds dashboard build root directory to `apps/api` → trigger/verify a production deploy. Rationale: the running worker is unaffected until the next deploy, so the failure window only affects builds of the intermediate state, not the serving production worker. Updating the dashboard before the merge would break builds for the opposite reason (`server/api` still exists with old code, but the setting wouldn't match). The dashboard step is a manual task with explicit verification (a successful Workers Builds run + healthy worker), not something CI can do.

### D5: Local `.dev.vars` moves by hand

`server/api/.dev.vars` is untracked (gitignored) and contains local secrets — `git mv` cannot move it and it must never be committed. The apply steps include a plain shell move of this file. Alternative considered — documenting it only: rejected, forgetting it breaks the next `wrangler dev` with a confusing missing-secret error.

### D6: Update all stale path references in docs and comments

`README.md` (structure table, deploy, migrations, env vars, verification) and the `server/api/src/schemas` comments in `packages/schemas/src/*.ts` change to `apps/api/src/schemas`. Rationale: comments are the cheapest thing to get right now and the most expensive to discover wrong later, especially for agents following AGENTS.md-style conventions. This is documentation hygiene within scope, not new scope.

### D7: Web test flake — raised timeout and fixed the test's render race (added during apply)

CI failed on the recurring-expenses combobox test (added in `d2c73ba`) with two distinct shapes, both rooted in the test racing the page's async auth gate rather than the move (this change touches no web code):

1. **Local full-gate runs (3/3)**: the file exceeded Vitest's 5 s default `testTimeout` under CPU saturation (1.7 s standalone → 11.9 s full gate). `apps/web/vitest.config.ts` gets `testTimeout: 30_000` with an explanatory comment, matching both API configs, which already document this exact failure mode.
2. **CI**: the page's auth gate (`recurring-expenses.tsx` returns a gate screen while the stubbed `/api/auth/me` query is pending) means the "New recurring rule" button exists only after the query continuation re-renders — and test 1 clicked it with a synchronous `getByRole`, winning the race only on fast machines. The click now uses `await screen.findByRole(...)`, the same deterministic pattern the adjacent test in the file already uses.

The timeout raise alone did not fix CI because the element-absence race is unrelated to the assertion timeout; the test fix is the root-cause repair, and the timeout stays as headroom for contended runs. Alternatives considered for the timeout: verifying the gate only serially (weaker evidence, CI still at risk) and deferring to a separate change (leaves CI red, blocking the merge). The user did not respond to the first pause prompt, so the established in-repo pattern was applied as the reversible default.

- [Workers Builds dashboard misconfigured or forgotten after merge] → Explicit task with verification criterion (a successful deploy from `apps/api`); brief deploy-failure window is bounded and doesn't affect the already-deployed worker. Rollback: revert the dashboard root to `server/api` plus `git revert` of the move commit.
- [Stale turbo cache entries from the old paths] → Harmless: turbo hashes inputs including paths, so old entries never replay into the new location; worst case is one uncached rebuild.
- [`pnpm-lock.yaml` merge conflicts if other work lands concurrently] → Move lands as an isolated small change on its own branch; lockfile regenerates deterministically via `pnpm install`.
- [`wrangler types` output (`worker-configuration.d.ts`) embeds old absolute paths] → Regenerate with `pnpm --filter @finance-application/api types` after the move and inspect the diff; generated file is already biome-ignored.
- [Rename detection fails for heavily edited files (e.g. `wrangler.jsonc`)] → Acceptable: only one file is edited post-move, and its history is not operationally load-bearing.

## Migration Plan

1. Repo change on a branch: `git mv`, patch `wrangler.jsonc`, update workspace globs, `pnpm install`, update docs/comments, run the full gate (`turbo run typecheck lint test build test:workers`).
2. Merge to `main`.
3. Update Cloudflare Workers Builds dashboard build root directory `server/api` → `apps/api`.
4. Verify a Workers Builds production deploy succeeds and the worker serves `/api/*` and the SPA.
5. Rollback strategy: revert the repo commit and set the dashboard root back to `server/api`; no database or data migration is involved, so rollback is complete.

## Open Questions

None. The deploy setup was confirmed by the user (Cloudflare Workers Builds, dashboard-configured build root directory).
